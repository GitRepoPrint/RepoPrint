# Keycloak

Infraestrutura pronta e login real ligado (frontend e backend). Checklist em `../RepoPrint-Backend/keycloack.md`.

- Serviço `keycloak` (26.8.1, `start-dev`) na consola `http://localhost:8080`, com as credenciais de admin do `.env`.
- Schema `keycloak` na BD principal, criado pela migração `4b7a9c1d2e30`; o serviço espera pelo `migrate`.
- Realm `repoprint` importado de `realm-export.json` só na primeira vez. Mudar o ficheiro não altera um realm já criado: para reaplicar, apagar o realm na consola (ou `docker compose down -v`, que apaga a BD toda).
- Variáveis `${NOME}` no ficheiro do realm são substituídas por variáveis de ambiente do contentor (os secrets usam `${KEYCLOAK_CLIENT_SECRET}` e `${KEYCLOAK_ADMIN_CLIENT_SECRET}`; a forma `${env.NOME}` não funciona e deixa o texto literal como secret).
- Login e registo por email são formulários do RepoPrint; as páginas do Keycloak só aparecem em erros do login com GitHub.
  - Client `repoprint-frontend`: confidencial, Direct Access Grant (password grant, formulários) e Authorization Code com PKCE S256 obrigatório (só o login com GitHub; redirect `http://localhost:3000/api/auth/callback`). Mapper `repoprint-api-audience` põe `repoprint-api` no `aud` do access token, que é o que o backend valida.
  - Client `repoprint-admin`: confidencial, só `client_credentials`; o utilizador do service account tem apenas o papel `manage-users` de `realm-management` (consegue criar e gerir utilizadores, mas não ler clients, roles nem fluxos). Cria as contas do `/signup`. Quem tiver o secret pode alterar palavras-passe de qualquer utilizador: guardá-lo como os outros.
  - `registrationAllowed` está a `false`: o registo pelas páginas do Keycloak está fechado, a única entrada é o `/signup` do RepoPrint (com as caixas de Terms e Privacy). A consola de conta do Keycloak (`/realms/repoprint/account`) continua a existir.
- Login por email ou username, palavra-passe de 12+ caracteres (sem ser o username nem o email), 5 falhas antes do bloqueio temporário (o Keycloak devolve a mesma resposta de "credenciais inválidas" durante o bloqueio, por isso a interface não consegue distingui-lo). Perfil de utilizador com username e email obrigatórios e nome próprio e apelido opcionais. Sem verificação de email nem recuperação de palavra-passe (o SMTP de desenvolvimento existe, ver "Tema, SMTP e licenças", mas os fluxos estão desligados).
- O Keycloak vê sempre o IP do servidor do Next (não do utilizador): o bloqueio por força bruta é por conta e o limite por IP está no Next (`src/lib/auth/rate-limit.ts`, em memória, por `X-Forwarded-For` quando existe).
- Issuer público `http://localhost:8080/realms/repoprint`. Dentro do compose, o backend busca o JWKS a `http://keycloak:8080/realms/repoprint/protocol/openid-connect/certs` e valida o `iss` público; o frontend fala com `http://keycloak:8080/realms/repoprint` (`KEYCLOAK_URL`).
- O backend usa o mesmo client `repoprint-admin` para apagar a conta (`DELETE /admin/realms/repoprint/users/{id}`) e para confirmar que o utilizador existe antes de criar a linha na BD (um token válido de uma conta apagada não a recria). Basta o papel `manage-users`.
- Variáveis no `.env` (modelo em `.env.example`): `KEYCLOAK_ADMIN`, `KEYCLOAK_ADMIN_PASSWORD`, `KEYCLOAK_PORT`, `KEYCLOAK_CLIENT_SECRET` e `KEYCLOAK_ADMIN_CLIENT_SECRET`.
- A password de admin só é usada quando a BD está vazia. Depois disso, mudá-la no `.env` não tem efeito: alterar na consola.

## Entrar e registar com GitHub (2026-11-16)
Botões "Continue with GitHub" (`/login`) e "Sign up with GitHub" (`/signup`, só depois de marcar Terms e Privacy). Uma conta nova fica criada e ligada ao GitHub num só clique, mas por duas autorizações no GitHub (primeira vez): uma para o Keycloak (login, scope `user:email`) e outra para a nossa app (token dos repos, scope `repo`).
- Mecanismo: o GitHub é um identity provider do Keycloak (broker, `kc_idp_hint=github`). O Next faz Authorization Code com PKCE (`/api/auth/github`, `/api/auth/callback`, cookie `rp_oauth` com `verifier`, `state`, `next` e `intent`, 10 minutos); o `repoprint-frontend` voltou a ter `standardFlowEnabled` (redirect `/api/auth/callback`, PKCE S256 obrigatório) e continua com o password grant dos formulários.
- Depois do login o callback chama `POST /github/signin/finish {intent}` no backend: se a conta já tem linha na BD é um login; se não tem e o `intent` é `signup`, cria-a; se não tem e o `intent` é `login`, apaga o utilizador que o Keycloak acabou de criar e volta a `/login?error=github_no_account` (o Keycloak cria sempre a conta no primeiro login pelo broker, por isso a recusa apaga-a logo; nunca chega a ter sessão nem linha na BD). Sem token do GitHub na BD segue para `/api/github/connect` (a ligação do passo 7, que acaba em `/repositories?github=connected`); com token vai para o `next`.
- O token do GitHub **não fica no Keycloak**: o IdP tem `storeToken: false` (o Keycloak guarda só a ligação `federated_identity`, id e username do GitHub, verificado na BD). O token que usamos vem da segunda autorização, feita com o nosso OAuth App.
- Fluxo `github first login` (no realm): só `idp-create-user-if-unique`. Um GitHub cujo email ou username já existe (por exemplo uma conta com palavra-passe com esse email) é recusado, **sem ligar contas automaticamente**: o email das contas com palavra-passe não é verificado (sem SMTP), por isso ligar por email deixava quem registasse o email de outra pessoa ficar com o GitHub dela ligado. A recusa mostra a página de erro do Keycloak ("User with email ... already exists. Please login to account management to link the account."; não há redirect de volta à app). Essas pessoas entram com a palavra-passe e usam "Connect GitHub" no menu. O email do GitHub tem de estar verificado e visível (scope `user:email`); sem email o Keycloak também mostra a página de erro. O username da conta é o login do GitHub.
- Contas criadas assim não têm palavra-passe (o Keycloak guarda `emailVerified: true`); só entram com GitHub. Sem SMTP não há recuperação.
- Dois OAuth Apps no GitHub: (1) o do Keycloak, callback `http://localhost:8080/realms/repoprint/broker/github/endpoint` (`KEYCLOAK_GITHUB_CLIENT_ID` e `KEYCLOAK_GITHUB_CLIENT_SECRET` no `.env`, lidos pelo realm no import) e (2) o do passo 7, callback `http://localhost:3000/api/github/callback` (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `TOKEN_ENCRYPTION_KEY`). Um OAuth App só tem um callback. Sem o (1) o botão leva ao erro do Keycloak. O realm só importa uma vez: depois de mudar `.env` ou realm, `docker compose down -v`.
- Frontend: `KEYCLOAK_PUBLIC_URL` (endereço do Keycloak que o browser vê, `http://localhost:8080/realms/repoprint`).
- Verificado de ponta a ponta com o Keycloak real e um GitHub falso (configurado nos `baseUrl`/`apiUrl` do IdP; num stack de teste, por Admin API): login de GitHub sem conta recusado e utilizador removido, registo, token só cifrado na BD e vazio no Keycloak, regresso, `state` forjado, cancelar no GitHub, email já usado, apagar conta com revogação, registo repetido. Não verificado: o GitHub verdadeiro nem a interface num browser.

- Produção: trocar `start-dev` por `start` com TLS e hostname próprios, e um utilizador da BD restrito ao schema `keycloak`.

## Tema, SMTP e licenças (2026-11-15)
- Tema de login `repoprint` (`keycloak/themes/repoprint/login/`, montado em `/opt/keycloak/themes/repoprint`): estende o tema `keycloak` com o visual escuro do RepoPrint, o logo e mensagens de erro em linguagem simples (email ou username já existente, GitHub sem email, GitHub falhou, sessão expirada). A página de erro ganha "Back to RepoPrint", que leva a `/login` (`rootUrl` e `baseUrl` do client `repoprint-frontend`). Só aparece em erros do login com GitHub e em pedidos inválidos.
- SMTP: o realm usa `KEYCLOAK_SMTP_HOST`, `_PORT`, `_FROM`, `_AUTH`, `_USER`, `_PASSWORD`, `_STARTTLS` e `_SSL`. Por defeito aponta para o contentor `mailpit` do compose (só desenvolvimento; os emails ficam em `http://localhost:8025`, `MAILPIT_PORT`). Em produção trocar por um SMTP a sério. Verificado: um email de "Update Your Account" enviado pela Admin API chegou ao Mailpit. A **verificação de email e a recuperação de palavra-passe continuam desligadas** (`verifyEmail` e `resetPasswordAllowed` a `false`): com o password grant, ligar `verifyEmail` bloquearia o login até a pessoa verificar o email, e não há ecrãs no RepoPrint para isso.
- Realm já criado: o import só corre na primeira vez, por isso numa stack existente o tema, o SMTP e o `baseUrl` não mudam sozinhos. Duas hipóteses: `docker compose down -v` (apaga os dados) ou, na consola (`http://localhost:8080`, realm `repoprint`): *Realm settings → Themes → Login theme = repoprint*, *Realm settings → Email* (host `mailpit`, porta 1025, from `noreply@repoprint.local`) e *Clients → repoprint-frontend → Root URL `http://localhost:3000`, Home URL `/login`*. Depois `docker compose up -d keycloak mailpit` (cria o `mailpit` e monta o tema).
- Licenças: `NOTICE.md` na raiz do repo (Keycloak Apache-2.0, PostgreSQL, Mailpit). Usamos as imagens oficiais sem alterações; só a configuração e o tema são nossos.
